就職活動で企業に提出するためのゲームを制作しています。工夫すべき点を教えてください。

就職活動用のゲームなら、「ゲームとして面白い」だけでなく、「自分が何を考え、どう工夫して作ったかが採用担当者に伝わる」ことを重視するとよいです。
特に工夫すると効果的なのは次の点です。

チュートリアルを長くしすぎない
2. 「自分ならでは」の要素を1つ入れる
たくさん機能を詰め込むより、「ここは自分が特に工夫した」と言えるポイントを1～2個作るほうが、作品の説明がしやすいです。

UI/UXへのこだわり

未完成の大型ゲームより、

のほうがポートフォリオとして見せやすいです。

ゲーム本体だけを提出するのではなく、

制作期間

担当範囲
工夫した点
苦労した点
今後改善したい点

採用担当者が必ずしも長時間プレイできるとは限らないので、1～2分程度でゲームの魅力と技術的な工夫が分かる動画があると便利です。
7. 「制作物」ではなく「制作過程」も見せる
Gitのコミット履歴、設計図、仕様変更、プロトタイプなどを見せられるなら、
「最初はこう考えたが、実際に試した結果こう変更した」
という過程を紹介すると、単なる完成品以上に開発力を伝えられます。
特におすすめの構成
もしゲーム系企業への提出を想定しているなら、
「短時間で遊べる小さなゲーム」＋「特徴的な技術要素」＋「制作過程をまとめたポートフォリオ」
という構成が作りやすいです。
例えば、
5～10分でクリアできるゲーム

↓

という流れにすると、「ゲームを作れる」だけでなく「考えて開発できる」ことを伝えられます。
もしよければ、**「どんなゲームを制作しているか（ジャンル・使用エンジン・制作人数・志望する企業/職種）」**を教えてください。そこまで分かれば、就活作品としてどこを工夫すると効果的か、具体的に一緒に考えられます。

ゲームの視点はトップビューを想定しています。設定として、プレイヤーは強制的にデスゲームに参加させられ、建物からの脱出を余儀なくされます。しかし、プレイヤーが進む道は一部が透明床になっており、そのままではどこが足場なのかわかりません。(見えないだけで足場としての判定はあります)そこで、プレイヤーは自身の血を使って足場をあぶり出すことになります。ゲーム性として、このゲームでは制限時間はありません。しかし、自傷すると時間経過でプレイヤーの体内の血液量が減っていき、致死量となるとGameOverとなります。つまり、プレイヤーの血液がパズルを解くための鍵となるとともに、制限時間にもなるのです。

この設定まで聞くと、ゲームの核がかなり明確です。
特に面白いのは、**「制限時間を設けない代わりに、プレイヤー自身の血液を制限リソースにする」**という設計です。
つまり、
時間は止まっているが、プレイヤー自身が時間を消費している
という構造になっています。
これは就活作品としても、ゲームデザインとプログラミングの両方を説明しやすい題材です。
ゲームの基本ループを一本化する
トップビューなら、私は次のループを中心に設計するのがよいと思います。
探索 → 血を使う → 足場を発見 → ルートを判断 → 移動 → 血を失う → 脱出
重要なのは、「血を使えば正解が分かる」ゲームにしすぎないことです。
例えば、
血を1滴使う → 小さな範囲だけ床が見える
血を多く使う → 広範囲が見える
しかし血液量は時間経過で減少する
一度見えた床も、時間が経つと再び見えなくなる
とすると、
「全部見てから進もう」
ではなく、
「最低限だけ見て、記憶しながら進もう」
という判断が生まれます。
これがパズルとしてかなり重要になります。
特におすすめしたいのが「血液の二重消費」です
現在の設定では、
自傷する → 血液を消費する → 時間経過でも血液が減る
ですよね。
ここを明確にすると、ゲームシステムが非常に綺麗になります。
例えば血液量を、
最大血液量 → 現在血液量 → 致死量
として管理します。
そして、
自傷による即時消費
＋
時間経過による継続消費
という2種類のコストを持たせます。
するとプレイヤーは、
「今ここで血を使う必要があるか？」
だけでなく、
「ここで血を使ったら、この先どれだけ探索できるか？」
まで考えることになります。
これなら「制限時間○○秒」という一般的なゲームとは違って、プレイヤー自身が残り時間を作っている感覚を出せます。
トップビューだからこそできること
トップビューとの相性もかなり良いです。
例えば画面上では、
┌─────────────────────┐
│  ■■■        ■■■       │
│  ■  ■   ○    ■       │
│  ■  ■ ~~~~ ■■■       │
│       ~~~~            │
│   ■■■       ■■■      │
│             ▲        │
│          プレイヤー   │
└─────────────────────┘
最初は透明床が見えない。
プレイヤーが自傷すると、その周囲だけ、
      ┌──────┐
      │透明床│
      │透明床│
      └──────┘
のように浮かび上がる。
このとき、血が「情報を取得するためのリソース」になっているわけです。
ここがこのゲームの一番重要な部分だと思います。
「血で見える」をプログラムとしてどう作るか
プログラマ志望なら、ここは作品紹介でかなり深掘りできます。
例えば床を、
class Floor
{
    Vector2 position;
    bool isSolid;
    bool isVisible;
    float bloodAmount;
};
のような概念で管理して、
isSolid → 足場として存在するか
isVisible → プレイヤーから見えているか
bloodAmount → どの程度血が付着しているか
を分離する設計ができます。
すると、
「見えない＝存在しない」ではない
という、このゲーム独特のルールをコード上でも明確に表現できます。
さらに一歩進めて、
Floor
 ├─ Collision
 ├─ Visibility
 ├─ Blood
 └─ VisualEffect
のように、ゲーム上の役割と描画処理を分離すると、設計面でアピールできます。
実際のコードはプロジェクトの構成に合わせればよいですが、就活ではこうした**「なぜこの構造にしたのか」**を説明できることが重要です。
「血が広がる処理」は技術アピールにもなる
さらに余裕があるなら、血を単なる円形エフェクトにせず、
床の上に血が広がって透明床を可視化する
ようにすると面白いです。
例えば、
自傷
 ↓
血液エフェクト発生
 ↓
床との接触判定
 ↓
床に血が付着
 ↓
可視化率が上昇
 ↓
一定時間経過
 ↓
血が乾く
 ↓
可視化率が低下
というシステムです。
これなら、
座標計算
当たり判定
オブジェクト管理
時間による状態変化
描画
エフェクト
ゲーム状態管理
など、プログラマとして説明できる要素が自然に発生します。
もう一つ重要なのが「プレイヤーに何を見せるか」
このゲームでは、見えない床を全部見せてしまうとパズルが成立しなくなるので、情報量の設計が重要です。
例えば、
A. 血が付いた部分だけ完全に見える
最も分かりやすい方式。

C. 一度発見した床は記憶される
血が乾いて床が見えなくなっても、
「さっきここに足場があった」
というプレイヤーの記憶だけが残る。
これはパズルとの相性がかなり良いです。
「見るために血を使う」→「覚える」→「血を節約する」
というプレイヤーの学習が生まれるからです。
デスゲーム設定は「ゲームシステム」と結びつける
設定についても、単なるストーリーとして置いておくより、
なぜ主人公が血を使わなければならないのか
をゲーム内で説明できると強くなります。
例えば、
建物内の特殊な床は肉眼では認識できない。
主催者は参加者に自身の血液を使わせることで、床を一時的に可視化できる装置を用意している。
など。
そうすると、
世界設定 → 血液システム → パズル → GameOver
が一本につながります。
就活作品としては「3つの技術」を見せると強い
最終的には、作品紹介をこの3本柱にするとまとまりやすいと思います。
① 血液システム
血液量をリソースとして管理し、ゲームの進行とGameOver条件の両方に利用。
② 透明床システム
「存在するが見えない」という状態を、当たり判定と描画を分離して実現。
③ パズル・ゲーム状態管理
プレイヤーの行動、血液量、床の可視状態、時間経過などを連動させて管理。
この3つなら、単に「DxLibでゲームを作りました」ではなく、
「ゲームデザイン上の要求を分析し、それをC++でシステムとして設計・実装した」
という見せ方ができます。
そして、この作品では**「制限時間がないのに、血液が減ることで実質的な時間制限が発生する」**という部分を、作品紹介の最初に持ってくるのをおすすめします。
たとえば作品概要の一文を、
「時間制限のない脱出ゲーム。ただし、床を可視化するために自らの血を使うたび、プレイヤーの生存可能時間が短くなる。」
とすると、かなりゲームの特徴が伝わりやすいです。
もし次に進めるなら、**このゲームの「1ステージを実際にどう設計するか」**を考えるのがかなり重要です。
特に「どこで血を使わせるか」「血を使わないとどう困るか」「どこまで見せればプレイヤーが推理できるか」を具体的なステージ例に落とすと、ゲーム性が一気に固まります。

VisualStudoi2022とDxライブラリを用いてゲーム制作を行っています。現在ディレクトリの構造が以下のようになっており、SaveLoad.cppの処理でgamedata.datにゲームの進行状況を書き込もうと思っています。SaveLoad.cpp内で1gamedata.datのパスを指定するとき、どのように記述すればよいでしょうか。

GameProject/
|-game-data/
|  |-gamedata.dat
|-sourcer/
   |-core
      |-SaveLoad.cpp
      |-SaveLoad.h


この構成の場合、**実行時のカレントディレクトリ**が `GameProject` になるようにVisual Studioから実行しているなら、`SaveLoad.cpp` では次のように指定できます。

```cpp
"game-data/gamedata.dat"
```

またはWindows環境なので、

```cpp
"game-data\\gamedata.dat"
```

でもOKです。

例えば、

```cpp
FILE* fp = fopen("game-data/gamedata.dat", "wb");
```

と書けば、

```text
GameProject/
├─ game-data/
│  └─ gamedata.dat   ← ここ
└─ sourcer/
   └─ core/
      ├─ SaveLoad.cpp
      └─ SaveLoad.h
```

の `gamedata.dat` を開こうとします。

### 重要な点

ここで注意したいのは、**パスは `SaveLoad.cpp` の場所を基準にするわけではない**ということです。

例えば、

```cpp
"../../game-data/gamedata.dat"
```

とは基本的に考えません。

相対パスは通常、**プログラムを実行したときの「カレントディレクトリ」**を基準に解釈されます。

Visual Studio 2022では、プロジェクトの設定によってカレントディレクトリが変わる可能性があります。

そのため、ゲーム制作では例えば、

```cpp
const char* savePath = "game-data/gamedata.dat";
```

としておき、Visual Studioの

**プロジェクトのプロパティ → デバッグ → 作業ディレクトリ**

を確認して、

```text
$(ProjectDir)
```

など、`GameProject` を指すようにしておく方法が分かりやすいです。

もし現在、**「Visual Studioから実行すると `gamedata.dat` が見つからない」**という問題が起きているのであれば、Visual Studio 2022の設定画面を含めて、**このディレクトリ構成で確実にセーブできる設定方法**を順番に説明できます。

今のところ、各キャラクター名や状態異常名の文字列を1つのファイルにまとめておき、描画する際にsprintf関数を用いて描画用の配列に書き込むようにしています。書き込む状態異常の文字列は条件分岐を用いて変えています。
以下が実際のコードです。この実装の仕方よりも適したやり方があるような気がするのですが、どうすればよいか分からず困っております。良い方法があれば教えていただけないでしょうか。
